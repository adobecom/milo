# Block Breakdown

Used by SKILL.md Phase 3.5 (URL Mode and Script Output Mode only — not available in Trace Mode, which has no DOM access). Builds a per-component/per-block performance dashboard from data **already collected** by `agents/metrics-collector.md`'s two passes — network weight, GPU pressure, CPU time (baseline vs. throttled), and Core Web Vitals, broken out by the page's component blocks rather than aggregated page-wide.

**This file does not run any additional test passes against the target page.** All measurement happens inside `agents/metrics-collector.md`'s baseline and throttled passes (`isMiloSite` / `blockBreakdown` fields on each `MetricsBundle`). This file only: (1) builds the chart from that already-collected data, (2) writes the per-block findings, (3) renders and screenshots the chart HTML — which is a *separate* browser navigation, but to a local file server showing a chart we generated, not a third test of the audited page.

This exists because the page-wide CDP counters (`taskDurationS`, `layoutDurationS`, etc.) cannot answer "which block is the problem" — only "how bad is it overall." The `blockBreakdown` field gets real, attributable per-block numbers instead of guessing from block names or animation selectors.

## When this runs

Only when `baseline.isMiloSite` is `true` (set by `agents/metrics-collector.md`, using the convention that a block is a `<div>` whose parent has class `section`, and `block.classList[0]` is the block's name). If `false`, SKILL.md Phase 3.5 skips this file entirely.

If a local milo checkout is available (cwd or a known path contains `libs/c2/blocks/`), you may cross-reference `baseline.blockBreakdown.blocks` against that directory's contents (`ls libs/c2/blocks/`) when writing findings, to confirm a block name corresponds to an actual C2 component before making claims about its source file.

## What each field measures (and what it can't)

| Field | Method | Reliability |
|---|---|---|
| **`perBlock[block].netKB`** | Resource Timing entries, each resource mapped to its containing block by DOM ancestry. Computed on **both** passes (not gated by profile) — present as **two columns**, `baseline.blockBreakdown.perBlock[block].netKB` and `throttled.blockBreakdown.perBlock[block].netKB`, same as CPU. | High — reproducible run to run, but **not throttle-invariant**: a real network throttle can mean a resource simply hasn't finished downloading within the same fixed settle window, so throttled can genuinely show less (or, if a retry/fallback path kicks in, more) than baseline. Do not assume they'll match — a block that shows real KB on baseline and 0 on throttled is telling you something (its resource didn't arrive in time under slow network), not a measurement error. |
| **`perBlock[block].layerCount`** | Count of elements per block with an active `will-change` (≠ `auto`) or CSS animation (`animationName` ≠ `none`) | High — DOM-structural, reproducible run to run, and genuinely throttle-invariant (it's a static count of elements/styles, not a runtime measurement) — read from `baseline` only; this is the one field where a single column is correct. |
| **`perBlock[block].cpuMs`** | Real Chrome trace (CDP `Tracing` domain), captured from right after navigation through decoration, the synthetic click-pass, AND scroll — one continuous window, not scroll-only — summed by source file, mapped to block by filename. Present as **two columns**: `baseline.blockBreakdown.perBlock[block].cpuMs` and `throttled.blockBreakdown.perBlock[block].cpuMs` — never collapsed into one number. | Medium — **varies between runs** on live production sites (third-party/personalization content differs per load). A block whose ms scales roughly with the throttle's CPU rate (~4×) is a genuine CPU cost; one that barely moves (or moves less than 4×) is likely dominated by something other than script execution. **A block that shows a cost on baseline and drops to ~0 under throttle is a red flag, not a clean result** — CPU-bound work only ever scales *up* under more throttle, never down to nothing. Treat that inversion as a sign the baseline reading was itself an artifact (e.g. test-induced side effects like an opened modal — see the synthetic-click caveat in `agents/metrics-collector.md`) rather than reporting "baseline has an issue, throttled doesn't" at face value. **If every block reads 0ms on both passes, that is itself a red flag, not a clean result** — a live page always has *some* decoration cost; check that the trace actually started before the settle loop (not just before scroll — a scroll-only window structurally misses init-time cost, which is where most block-authored JS runs) before reporting a page as CPU-clean at the block level. |
| **`perBlock[block].forcedMs`** | Long Animation Frame API, summed `forcedStyleAndLayoutDuration` per block, same full post-navigation window as CPU above | **Low / best-effort.** LoAF only reports for frames that already qualify as "long" — frequently all-zero even when page-wide recalc/layout time (`cdp.recalcStyleDurationS`/`cdp.layoutDurationS` on the MetricsBundle itself) is high. When this happens, report the page-wide totals as a **not attributable per block** callout instead of fabricating a split. |
| **`blockBreakdown.lcp`** | Largest Contentful Paint's final candidate element, attributed to a block. Captured as a **snapshot immediately after settle, before the synthetic click-pass or scroll** — not read at the end of the pass. | **Page-level, not per-block by nature** — exactly one LCP winner. Report as a page-wide stat naming the block, not a chart column. Read from **both** `baseline` and `throttled`. The pre-scroll snapshot timing matters a lot here: a live trace proved LCP resolves correctly and stably right after settle (e.g. 848ms, a video poster), then a scroll wheel event — which the LCP spec says should *stop* new candidates from being recorded — instead triggered a lazy-loaded background image to load and get recorded as a new, much later "winner" (22,740ms) that was never the real LCP. Reading LCP after scroll reports that artifact, not reality; the pre-scroll snapshot is what's authoritative. If you ever see LCP reported from this skill at a value that looks like it lines up with when scrolling started rather than initial paint, suspect this exact bug before trusting the number. |
| **`blockBreakdown.cls`** | Layout Shift entries (`hadRecentInput` excluded), summed for the total, attributed per block via the shift source node. Same pre-scroll snapshot timing as LCP above. | Total is reliable; **per-block attribution frequently comes back empty** — third-party ad/tracking iframes are a common CLS source and their internal DOM isn't reachable from the parent document. When `cls.byBlock` is sparse/empty despite a non-zero `cls.total`, say so and name the likely external cause (check the page for ad/tracking iframes) rather than implying no block-level shift occurred. |
| **`blockBreakdown.inp`** | Discrete-interaction event timings (`click`/`keydown`/`keyup`/`pointerdown`/`pointerup`) from a safe synthetic-click pass (buttons only), attributed via `.target` | Often close to unmeasurable: many pages' interactive elements (nav/header controls) live outside `<main>` entirely — structurally outside every block. If `inp.byBlock` is empty or sparse, check `inp.eventCount` and say explicitly whether that's because few blocks *have* clickable elements, rather than reporting a clean "no issue" that's actually "nothing was measurable." |

Never present any of these numbers with false precision. `0` or a missing key means "not observed this run," not "definitely zero cost."

**Never include commentary about this skill's own internal bugs, fixes, or debugging history in the report or chart** (e.g. a "Fixed this run" / "previously wrong" banner). The report is about the *page's* performance, not this tool's development process — if a prior run's numbers were wrong, just report the correct numbers now, with no meta-narration about why an earlier run differed.

**The page-wide CPU/runtime comparison is the primary subject of this audit and must be the most visually prominent section of the chart — not a plain data table blended in among CWV/resource sections.** Render `cdp.taskDurationS`, `cdp.recalcStyleDurationS`, `cdp.layoutDurationS`, `totalBlockingTimeMs`, long-task count/worst, jank-frame count, and avg FPS (baseline vs. throttled) as a dedicated high-contrast panel — larger type than every other section, placed near the top (right after the title/subtitle, before per-block or CWV detail) — since this is what the audit is fundamentally measuring. Everything else (resource totals, CWV, per-block breakdown) is supporting detail underneath it.

## Step 1 — Build the dashboard

Invoke the `dataviz` skill for palette/mark guidance. Build a small-multiples horizontal-bar dashboard with **one row per block** (from `baseline.blockBreakdown.blocks`), **five columns**: Network-baseline KB / Network-throttled KB / GPU-pressure count / CPU-baseline ms / CPU-throttled ms — same block order in all five columns (sort by baseline network KB descending — it's usually the most stable dimension). Within each metric pair, throttled always sits to the right of baseline. GPU pressure is the one column that stays single — it's a static DOM/CSS count, not a runtime measurement, and is genuinely identical between passes (verify this against `baseline.blockBreakdown.perBlock[block].layerCount === throttled.blockBreakdown.perBlock[block].layerCount` while building the chart; if they differ, something else has gone wrong, since nothing about the DOM should change based on CPU/network conditions). Label the throttled columns precisely — "4× CPU + network throttle," not just "throttle" — since it's a combined profile.

**Color assignment — by category, never by block.** Each metric gets one hue, with baseline/throttled as two shades of that hue (lighter = baseline, darker = throttled) — this pairing convention (already used for CPU) now extends to Network too: Network-baseline/throttled = slot-1 blue (light/dark), GPU pressure = slot-3 aqua/green (single shade, no throttle pair), CPU-baseline/throttled = slot-2 orange (light/dark). Baseline/throttled as two shades of one hue signals "same metric, two conditions," matching how the rest of this skill treats baseline vs. throttled. Never recolor a specific block's bar to "highlight" it — a legend that reads "orange = the block we've been discussing" is a highlight scheme, not a category legend, and reads as arbitrary the moment there's a second block of interest. If a block needs calling out, do it in the written text, not through a one-off color. Always include the full legend (every color used, plus a "— = not observed" marker) directly under the chart title.

**After building the chart, verify the legend against the actual rendered markup, not against intent.** A real instance of this drifting: the legend promised "Network — baseline (light) / throttled (dark)" while every network bar in the table actually used the same dark shade for both columns (the light variable was defined in CSS but never referenced) — caught only by comparing the legend text to the literal `background:` value on each bar-fill. Check every color swatch the legend promises actually appears where promised before finalizing.

**All bars within one metric+condition pair share a single scale across every row — never scale a row against its own value.** A real instance of this drifting: one block's network bar was drawn at 100% width scaled against *its own* KB value while every other row was scaled against a different, smaller reference point, making bar-width comparisons across rows meaningless even though they looked visually calibrated. Compute one shared max (the largest value across all blocks and both baseline/throttled columns for that metric) and scale every bar in that metric against it — even if that makes most bars tiny slivers next to one dominant block. That's not a rendering problem to fix, it's the actual finding (say so in the caption: "most blocks are genuinely tiny next to X").

**Any metric that inverts direction in a way a skeptical reader would flag — i.e. it looks *better* under throttle — needs its own one-line caveat inline, not silence.** JS heap dropping under throttle is a real recurring example: it looks like an improvement but actually means less script finished executing within the test window, not less work per script. Don't let a counterintuitive number sit unexplained next to metrics that all move the expected direction — it reads as an error if unaddressed.

**State each page-level fact once, not in the banner, the CWV section, and a findings card.** Pick the one location that should carry the full explanation (usually the findings card, since that's where the fix belongs) and keep every other mention to a short pointer/number with no restated narrative. A real instance of this drifting: the same "~90s vs ~18s decoration" fact and the same LCP regression narrative each ended up fully explained in two or three places with no new information added on repeat — cut the repeats, keep the fix-bearing location whole.

Above the chart, include a Core Web Vitals section built from `baseline.blockBreakdown.lcp`/`.cls`/`.inp` and `throttled.blockBreakdown.lcp`:
- LCP: both readings, flagging explicitly if the winning element/block differs.
- CLS: total for both passes, plus per-block attribution where non-empty, with the ad-iframe caveat if `cls.byBlock` is sparse.
- INP: what was actually measurable, naming the ratio of blocks with vs. without a clickable element if `inp.byBlock` is sparse.
- The page-wide `cdp.recalcStyleDurationS`/`cdp.layoutDurationS` totals from **both** MetricsBundles, labeled "not attributable per block."

Do not add a separate "what each column measures" footnote paragraph below the chart — that explanation lives in the per-block findings cards (Step 2) and in the column headers/legend themselves.

## Step 2 — Written per-block, per-category findings (always required, not optional)

The chart alone is not the deliverable — every block, in every category, needs a verdict: what was measured, whether it constitutes an issue, and if so, the fix. Do not skip blocks that show no issue; state "no issue" explicitly so the report reads as complete. Exception: skip blocks that are purely structural/metadata with no visual or behavioral footprint by nature (e.g. a `section-metadata`-style block used only to carry authoring config, never rendered, or a `visually-hidden`-style accessibility skip-link with no visible rendering) — there is nothing to verify or explain for these, and a full card for them is noise, not completeness. Every block that renders anything or runs any code still gets a card. Still show these blocks' raw numbers in the per-block chart table itself (that's just data, not analysis) — only skip them in the written findings cards.

For any row with a real finding (MEDIUM/HIGH), don't stop at naming the symptom — give the actual root cause from source (function name, line number, what the code does) and a fix specific enough to act on without re-deriving it, not generic advice like "optimize this" or "consider debouncing." A one-line "unconditional will-change, scope it to :hover" is acceptable only if that's genuinely the whole story (e.g. a hover-only class already exists in the block's own JS and the fix really is a one-line selector change); if the real cause is more involved (e.g. a layout-thrashing pattern spread across several call sites, or an existing interaction-state class that only covers part of what triggers the cost), say so and describe the actual gap rather than flattening it into generic guidance.

Before writing a GPU or CPU verdict for any block with a non-zero value, **verify against source** the same way `agents/trace-analyser.md` Step 0 requires — do not infer a fix from the block name alone:

- **GPU non-zero count**: grep the block's own CSS for `will-change`. If found, check whether it's declared inside the base rule (unconditional — a real antipattern, since the layer persists for the element's entire lifetime for a transition that only fires on hover/interaction) or gated behind `:hover`/`:focus-visible`/an interaction-toggled class (defensible). Separately check whether the element's class matches `[class*="parallax-"]` or is otherwise wired to `animation-timeline` — if so, cross-reference the shared utility (commonly a site-wide `styles.css`, not the block's own file) rather than attributing the pattern to the block's own code; a scroll-timeline-driven `will-change` matching the animated properties is materially more defensible than a permanent one, even though both count toward the same "GPU pressure" number. If the block's own CSS has **no** `will-change`/`animation-name` at all despite a non-zero count, the count is coming from a shared global utility applied to elements inside it — say so explicitly.
- **CPU non-zero ms**: grep the block's own JS for the likely cause (`addEventListener('scroll'`, unthrottled handlers, `getBoundingClientRect`/`offsetHeight`/`offsetWidth` reads inside them). Name the actual line(s) found. If nothing stands out for a small (<20ms) value, say the number is too small to warrant a code change rather than inventing a cause. Report baseline and throttled as two separate verdicts (they can carry the same fix) — check whether throttled ≈ baseline × 4: close to that ratio confirms the cost is genuinely CPU-bound; a ratio much lower than 4 suggests part of the measured time isn't pure script execution, worth a one-line caveat.
- **Network non-zero KB**: check `resourceSummary`/`resourceTotals` (already on the MetricsBundle) for what resource type is driving it (video / image / script) before writing the fix — the fix differs materially. Compare baseline vs. throttled explicitly: if throttled shows meaningfully less KB than baseline for the same block, that resource likely didn't finish loading within the settle window under the slower network — worth calling out as its own finding (the resource is at risk of never arriving for a real slow-connection visitor), separate from whatever baseline's weight already flagged.
  **Before recommending lazy-load for any heavy resource, check the block's position on the page:**
  ```javascript
  const sectionIndex = [...document.querySelectorAll('main > .section')].findIndex(s => s.querySelector(`.${blockName}`));
  ```
  A block at index 0 (or 1, if index 0 is only a `visually-hidden` skip-link) is the **hero/first block** — likely the LCP element or directly adjacent to it, already in the initial viewport. **Never recommend lazy-loading it** — that delays the exact thing LCP measures. For a heavy resource there, the fix is the opposite: compress/re-encode at correct resolution and bitrate, `fetchpriority="high"`, `preload="auto"`, or a shorter/lighter loop. Cross-check against `blockBreakdown.lcp.block` too — if a *different* block actually won LCP, that block needs the same non-lazy-load treatment, not just the first one.

Each block gets one card with three labeled rows — Network, GPU, CPU — each showing baseline→throttled inline (e.g. "22ms→61ms") rather than splitting baseline/throttled into separate rows; the arrow notation already shows both numbers side by side without doubling the row count. Every block gets all three rows stated explicitly, including blocks with zero footprint everywhere ("0ms both passes") — do not skip a block just because nothing is wrong; an absent card reads as "not checked," not "clean." Each row carries its own OK/MEDIUM/HIGH tag (never omit the tag) so the report is scannable without reading every sentence. Order block cards to match the per-block chart's row order (baseline network descending).

**Each row is two lines, not one flex line — a short tag header, then a full-width paragraph.** A single `display:flex` row containing the category tag + OK/MEDIUM/HIGH tag + condition label + a long description all as inline siblings breaks once the description is more than a few words: the fixed-width tag elements squeeze the remaining flex space down to almost nothing, and the description wraps into a near-vertical column of single words instead of normal prose (confirmed by direct observation — screenshots showed exactly this once description text grew past a short phrase). Structure it as `<div class="row-head">` (the tags, `display:flex`) directly followed by `<p class="row-text">` (the description, block-level, `padding-left` matched to the tag header's width so it visually aligns underneath) — never put the description text as a flex sibling of the tags.

**Only rows with an actual MEDIUM/HIGH finding carry a condition label — never put one on an OK row.** "Affects: baseline + throttled" on a clean result is meaningless (there's nothing to affect); state the OK verdict plainly instead. For rows that do have a finding, use precise plain language, not the terse `baseline + throttled` jargon: `only when throttled` (the issue doesn't happen — or isn't measurable — on a fast connection), `present in both, gets worse when throttled` (a real cost that exists either way but scales up), or `structural — same in both, unrelated to throttle` (a DOM/CSS/markup property, like an oversized image or an unconditional `will-change`, that has nothing to do with network/CPU conditions and would read identically on any connection). If a single row bundles two distinct sub-findings with different conditions (e.g. a CPU cost present in both passes plus a forced-layout cost that only appears under throttle), give each sub-finding its own label rather than one covering both.

**This written report renders inside the chart image itself, below the bars — not only as chat text.** Add a `.findings` section to the same HTML file the chart lives in, then re-screenshot the whole file so the image is self-contained.

## Step 3 — Render and clean up

This project has no local dev server assumption — serve the chart HTML over a throwaway local HTTP server, since headless Chrome cannot load `file://` URLs in this environment. Use `python3 -m http.server <port> --directory <dir>` (backgrounded via Bash) rather than `cd <dir> && python3 -m http.server <port>` — the `--directory` flag avoids a leading `cd &&`, which matters because permission-allowlist rules match the whole command string as a prefix, and a chained `cd ... && ...` command won't match a rule anchored on the tool name (e.g. `Bash(python3 -m http.server *)`). Keep this same habit for every other command in this step too (`sips`, `rm`, `mv`, `pkill`) — always pass full/absolute paths as arguments instead of `cd`-ing first, so each command starts with the tool name and stays matchable by a simple allowlist rule. Navigate Playwright to `http://localhost:<port>/<file>.html`.

- **This host's `window.devicePixelRatio` is not a clean `1` or `2` — it can be a non-integer value like `1.1`.** Confirmed directly, at length: on such a host, a `page.screenshot({ clip: {...} })` call (whether via raw Playwright or the `browser_take_screenshot` MCP tool, and regardless of `scale: 'css'` vs `'device'`) does **not** properly rescale the clip region — it treats the requested CSS-pixel width/height as a hard native-pixel output size and simply truncates the render to that many native pixels, silently dropping the outer ~1-(1/DPR) of the content (e.g. at DPR 1.1, the right/bottom ~9% of everything gets cut). This is insidious because `sips -g pixelWidth` on the result shows exactly the dimensions you asked for — nothing looks oversized or wrong until you actually read the pixels and find mid-word text clipping or bar-chart labels silently missing (confirmed: `.bar-track { overflow: hidden }` at 100% fill combined with this truncation made a value label vanish completely, with zero visual trace it was ever supposed to be there).
- **The fix:** read `window.devicePixelRatio` right before capturing. If it's not `1`, request the clip at `{ width: cssWidth * dpr, height: cssHeight * dpr }` (not the raw CSS dimensions) — this makes Playwright's internal truncation land exactly at the true edge of the content instead of inside it. Then downsample the result back to the intended CSS size with `sips --resampleWidth <intended-css-width> <path>` (same tool call as the HiDPI case below, different reason for needing it).
- **Verify by reading actual pixels, not just DOM measurements.** `getBoundingClientRect()`/`Range.getClientRects()` on the live page will report perfectly in-bounds coordinates even when the *painted* output is being truncated — the DOM has no visibility into this bug, since it happens in the screenshot pipeline after layout. The only reliable check is cropping the actual output PNG (e.g. via a quick Python/PIL script) at the specific regions most likely to sit near an edge (long paragraph lines, 100%-filled bar labels) and reading them back at native resolution before trusting the file.
- **Check the output file's actual pixel dimensions before opening it** (`sips -g pixelWidth <path>`) — on a HiDPI/Retina host, a screenshot can independently come out at 2-3× the intended CSS pixel width (confirmed directly: a 1300px-wide viewport produced a 3900px-wide PNG this way, a *different* bug from the truncation above — this one over-produces instead of truncating). Opening that oversized file makes macOS Preview auto-fit it small, so the report looks tiny/unreadable until the viewer manually zooms in. If the pixel width is more than ~1.5× the `.viz-root` CSS width, downsample it with `sips --resampleWidth <intended-css-width> <path>` before the final `open` call.
- Give text-bearing containers real margin, not the bare minimum — even after the DPR fix above, sub-pixel font rasterization can round a line's painted width very slightly wider than its computed layout width. A paragraph column sized with only a few px of slack before the container edge is one rounding error away from clipping its last word. Keep at least ~50-60px of unused horizontal margin in the overall chart width beyond what the content strictly needs.
- Kill the temporary HTTP server (`pkill -f "http.server <port>"`).
- Playwright's screenshot lands in the **current working directory**, not the scratchpad — move it into the scratchpad dir immediately.
- Delete any `.playwright-mcp/` directory the tooling drops into the project's working directory (console logs, snapshots) — it is not part of the user's repo and must not linger as untracked clutter. Always run this as `rm -rf .playwright-mcp` (relative to the project root, not an absolute path) — the exact same literal command every time, so it matches a fixed permission-allowlist rule regardless of whose machine/home-directory this runs on. Verify with `git status --porcelain` afterward.
- **Call `browser_close` as the last action of the entire skill run — this is the step that actually owns final cleanup.** `agents/metrics-collector.md`'s own close-on-throttled-pass only covers Phase 1/2; this file's chart-rendering navigation reopens/reuses the browser afterward, so if this file ran at all, it — not metrics-collector — is responsible for the final close. Skipping this leaves a Chrome process holding the Playwright profile lock indefinitely (observed firsthand: a stray process from a session days earlier blocked a brand-new session's browser launch with `Error: Browser is already in use for .../mcp-chrome-<id>`, requiring a manual `kill <pid>` to recover).
- **Run `open <path>` (macOS) on the final chart image as an unconditional last step, every single time this file runs — not a nice-to-have, not something to remember only when the user asks.** Ending a run without opening the chart means the user has to separately ask for it, every time, which they've already had to do more than once. The sequence every run ends on is: kill the temp server → move the screenshot to scratchpad → clean `.playwright-mcp/` → `browser_close` → `open <path>`. All five, in that order, every time.

Report the final image's scratchpad path to the user in the chat response too, alongside having already opened it — the path is for reference, the `open` call is what actually shows it to them.
