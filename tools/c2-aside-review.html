03 / The system principle

Separate the name,
the authoring, and the code.

These decisions should connect. They do not have to be the same decision.

01

What authors choose

A recognizable family name and a clear starter.

Design intent and content purpose should make the choice easier.
02

What authors fill in

Predictable fields, sensible defaults, and supported variants.

Don't ask authors to navigate an unrestricted collection of switches.
03

What engineering maintains

Shared code where responsibilities genuinely match.

Don't duplicate a block for spacing, or build one oversized universal block.

Different intent can justify a different recipe.
It does not automatically require duplicated implementation.

04 / The decision needed

One short conversation.
One bounded proof.

Leave with the chosen family, an owner, and the presentations we will support.

1 / Identify

Name the candidates

Which existing Aside is proposed? What specific content or behavior expectations distinguish this from a Card?

2 / Align

Choose the family

Agree on required fields, layout/background behavior, and supported variants. Keep Figma, authoring, and code aligned.

3 / Prove

Test one real example

Include a lockup, multiple actions, varied media proportions, and all device sizes. Have an author reproduce it from the guide.

Success: authors know what to choose, designs behave as specified, and shared fixes don't require several near-identical implementations.

Preserve existing pages.Keep Social Proof migration separate.Avoid duplication and variant overload.
